# Question bank authoring brief

Read first: `docs/DUE-DILIGENCE-OPERATING-CONTRACT.md`,
`architecture/ECHELON-CURRENT-STATE-BRIEF.md`, `questions/TAXONOMY.json`,
`sources/SEED-IDS.json`, and the schemas in `schemas/dd/`.

## Output (per assigned category code CAT)

- `questions/CAT.jsonl` one question per line, ids `DDQ-CAT-0001`...
- `answers/CAT.jsonl` answer units `ANS-CAT-001`...
- `controls/CAT.jsonl` controls `ECTL-CAT-001`...
- `evidence-requirements/CAT.jsonl` evidence requirements `EVR-CAT-001`...

Write files with a script (Python is fine) that builds records as data and serializes
with `json.dumps(record, ensure_ascii=False)`; do not hand-type thousands of JSON lines.
Every record must validate against its schema (`additionalProperties` is false).
Validate with `python3 -c "import jsonschema"` (installed) before finishing.

## What a good question is

- Materially distinct: differs in concern, tested control, required evidence or
  applicable population. Put rewordings (the way SIG, CAIQ, HECVAT, a bank, an insurer
  would phrase it) in `alternatives`.
- Written in original words. Never reproduce SIG, ISO, PCI or other licensed text.
- Realistic: something an enterprise, bank, wealth manager, DAF sponsor, insurer,
  auditor or procurement officer actually asks, or should ask given a real risk.
- Ranges from baseline (does a policy exist) through depth (how is it enforced, what
  evidence proves it, how is failure detected, how fast) to edge cases (exceptions,
  emergency access, failure modes, subcontractors, AI agents, multi-tenant effects).
- Include Echelon-relevant depth: F#/.NET, Limen browser boundary, Strata/PostgreSQL,
  AI agents performing engineering and operations, evidence generated by construction.

## Field guidance

- `source_refs`: at least one per question. Use seed IDs from `sources/SEED-IDS.json`
  (or `SRC-ECH-*`). `locator` is a control/section identifier you are confident of (for
  example `CC6.1`, `PR.AA-01`, `AC-2`, `A.8.28`, `Req 6.4.3`); if not confident, omit
  `locator` rather than guess. `basis`: `directly-documented` only when the source
  plainly addresses the topic; otherwise `reasonably-inferred`.
- `requirement_classification`: legal-regulatory only when a statute or regulation
  imposes it on a party in Echelon's position or on its customer in a way that flows to
  the vendor; otherwise the honest weaker class. Customers asking for something is
  `customer-preference` or `contractual-common`, not law.
- `industries`: from `financial-services`, `banking`, `wealth-management`,
  `donor-advised-funds`, `nonprofit`, `enterprise-software`, `healthcare`,
  `higher-education`, `public-sector`, `insurance`, `all`.
- `jurisdictions`: `US-federal`, `US-state:XX`, `US-states`, `EU`, `UK`, `global`.
- `products`: `echelon-organization`, `unbound`, `all-echelon-products`, or a named
  Echelon system.
- `answer_unit`: many questions per answer unit. Typical ratio 3 to 8 questions per
  answer unit. Each answer unit is the single answer to an underlying control concern.
- Answer unit honesty (critical): follow `architecture/ECHELON-CURRENT-STATE-BRIEF.md`.
  Expect most statuses to be `proposed-target-state` or `unknown`. `current_practice`
  says what is actually known (often "Unknown; no evidence located" or "Not
  established"). `provable` says what evidence exists now (often "Nothing").
  `customer_statement` is what we could truthfully say today; with
  `customer_statement_kind` of `planned` or `not-available` for non-existent
  capabilities. The `target_answer` is the strong, specific, ideally
  security-by-construction answer Echelon should be able to give.
- `challenge`: fill it for answer units where the conventional control is questionable,
  expensive, or replaceable by architecture or continuous evidence (aim for at least
  one in four answer units). Record opposing arguments honestly and separate technical
  effectiveness from institutional acceptance.
- Controls: prefer structural and automated controls; set `assurance_level` honestly
  (L1 elimination only within a defined scope). Cite Echelon rule IDs (SEC-*) and Unbound
  IDs (UNB-CTRL-*, SOC2-0xx, CNV-*) in `policies` / `related_external_controls` only
  if they exist (check `unbound/requirements/baseline/baseline.jsonl` and
  `unbound/requirements/governance/MASTER-ENTERPRISE-CONTROL-MATRIX.csv`).
- Evidence requirements: name the producing system only if it plausibly exists (see the
  brief); else `not yet assigned`. Freshness as ISO 8601 duration (`P1D`, `P90D`,
  `P1Y`) or `per-event`.
- Costs: use the coarse bands. `cost_basis` must say "order-of-magnitude judgment, not
  sourced" unless you have a source.
- `history`: one entry `{"date":"2026-11-25","change":"created","by":"research-agent"}`.
- No em dashes anywhere. American English.

## Finish

Report counts per file, the number of answer units with `challenge`, any source IDs
you needed but which were not seeded (list them, do not invent entries), and notable
gaps or contradictions found.
