# Due Diligence Research Operating Contract

This contract applies to every human or agent that writes research records in this
repository. It supplements, and never overrides, `AGENTS.md` (Praxis governance).

## Integrity rules (non-negotiable)

1. Never fabricate a source, URL, version, date, requirement, certification,
   implementation, test result, cost figure or assurance claim. If you cannot verify a
   fact, record it as `unknown` and add an open question.
2. Distinguish binding law and regulation, supervisory guidance, contractual
   convention, certification criteria, industry convention and customer preference
   (`requirement_classification`). Inclusion of a topic in a framework is not proof that
   it applies to Echelon or Unbound.
3. Never present a proposed control as implemented. Every answer carries one status
   from the controlled list in `schemas/dd/answer-unit.schema.json`. The
   `customer_statement` of an answer may only assert a current capability when the
   status is `verified-operational` or `implemented-not-independently-verified`; the
   build tool enforces this.
4. Never present internal verification as independent assurance. Use
   `assurance_independence` (`first-party`, `second-party`, `independent-third-party`,
   `regulatory-examination`).
5. Do not copy licensed questionnaire or standard text. SIG, ISO, PCI and similar
   content is restricted. Write original questions and cite the source and locator
   (control or section identifier) only. CSA CAIQ/CCM and NIST material are reusable
   under their stated terms; still prefer original wording.
6. Preserve contradictory evidence and objections. Do not delete an objection because
   it complicates the preferred Echelon approach.
7. Do not access confidential materials. Use only publicly accessible sources.
8. American English. No em dashes.
9. Do not modify any repository other than this one during the research phase.
   Recommendations for other repositories go to `recommendations/`.

## Evidence of current state

The authoritative current-state facts for Echelon systems are in
`architecture/ECHELON-CURRENT-STATE-BRIEF.md`, each tied to a repository and commit.
As of 2026-11-25 Echelon has no production deployment of Unbound, no SOC 2 report, no
ISO certification, no external penetration test and no formally adopted security
policy set beyond the proposed Secure Construction Standard v0.1. Answers must reflect
that. Most answers will therefore be `proposed-target-state` or `unknown`; that is the
correct and useful result.

## Record formats

| Record | Location | Format | ID pattern |
|---|---|---|---|
| Source | `sources/*.jsonl` | JSON Lines, `schemas/dd/source.schema.json` | `SRC-...` |
| Canonical question | `questions/<CAT>.jsonl` | `schemas/dd/question.schema.json` | `DDQ-<CAT>-<NNNN>` |
| Answer unit | `answers/<CAT>.jsonl` | `schemas/dd/answer-unit.schema.json` | `ANS-<CAT>-<NNN>` |
| Control | `controls/<CAT>.jsonl` | `schemas/dd/control.schema.json` | `ECTL-<CAT>-<NNN>` |
| Evidence requirement | `evidence-requirements/<CAT>.jsonl` | `schemas/dd/evidence-requirement.schema.json` | `EVR-<CAT>-<NNN>` |
| Proposed product requirement | `product-profiles/<product>/proposed-requirements.jsonl` | `schemas/dd/proposed-requirement.schema.json` | `DD-UNB-<AREA>-<NNN>` |
| Objection (adversarial review) | `validation/objections.jsonl` | `schemas/dd/objection.schema.json` | `OBJ-<PERSPECTIVE>-<NNN>` |
| Recommendation | `recommendations/*.jsonl` | `schemas/dd/recommendation.schema.json` | `REC-<TARGET>-<NNN>` |
| Open question | `research/open-questions.jsonl` | free-form with `id`, `question`, `context`, `blocking` | `OQ-DD-<NNN>` |

Category codes are defined in `questions/TAXONOMY.json`. Pre-allocated source
identifiers are in `sources/SEED-IDS.json`.

JSON Lines are canonical for high-volume records because thousands of one-record
Markdown files would be unindexed and expensive to load (see
`decisions/DDD-001-record-format.md`). Human-readable registers under `reports/` are
generated by `tools/build.fsx` and must not be edited by hand.

## Relationship rules

- One answer unit answers the underlying control concern. Many questions share one
  answer unit. Do not write a separate answer for a reworded question.
- Questions, answer units, controls, evidence requirements, policies and requirements
  are many-to-many and linked by identifier only.
- External repositories are referenced as `repo@commit:path` (for example
  `echelon-organization-administration@2763e576:policies/security/secure-construction-standard.md`)
  plus the rule identifier (for example `SEC-DB-001`).

## Materially distinct questions

A new question is warranted only when it differs in the concern it establishes, the
control it tests, the evidence it requires or the population it applies to. Wording
variants go in `alternatives`. The build tool flags near-duplicates.
